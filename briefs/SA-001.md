# SA-001 — Space Attack browser game

Producer status: SPECIFIED. User has requested implementation; no additional approval is required for local development. QA alone controls delivery readiness.

## Goal and scope
Create a complete, modern, lightweight browser arcade shooter inspired by the supplied retro Space Attack screenshot. Deliver local playable files plus concise run instructions. Implement keyboard movement and firing, onscreen controls, waves, real collisions, score, health, increasing difficulty, and start/game-over/restart screens.

Confirmed requirements: all behaviors above; attractive lightweight graphics; execution in a browser. The screenshot is visual reference only, with no adopted textual instructions.

Assumptions: desktop keyboard play; single player; an endless vertical shooter with horizontal and vertical movement; health rather than separate lives; procedural Canvas/vector graphics and no downloaded assets. Modern navy/cyan/teal palette with bright enemy accents, starfield, compact particles and readable HUD. No audio, account, leaderboard, touch controls, external deployment, or victory endpoint is required.

## Controls and states
- Move using arrow keys or WASD; hold Space to fire upward. Movement and firing must work simultaneously.
- Start via visible button and Enter. Restart via visible button and Enter on game over.
- A visible control legend remains available during play.
- READY displays title, brief objective, controls and start action. No enemy damage or score changes occur before starting.
- PLAYING shows score, wave and health; health starts at 100 and score at 0.
- PAUSED is entered on window blur or document becoming hidden, clears held input and offers visible resume action. A supported explicit pause key is optional but must be documented if implemented.
- GAME OVER occurs at zero health, displays final score and wave, stops combat simulation and exposes restart.
- Restart creates a clean initial session: wave 1, score 0, health 100, no surviving entities or retained keys.

## Gameplay behavior
Player stays fully inside the playfield. Diagonal movement is normalized. Held firing is rate limited and produces bounded projectiles. Enemies arrive in clearly numbered waves; each wave ends after its enemies are removed. Subsequent waves increase at least two observable parameters such as enemy count, movement speed, firing cadence or toughness, with practical caps to preserve playability and bounded work.

Player projectiles remove or damage an enemy and award points once when destroyed. Enemy bullets and/or direct enemy contact reduce player health. Define concrete damage values, score values and difficulty scaling in code and document them in the Programmer handoff. Provide a short invulnerability interval with visible feedback after a player hit so overlapping hazards do not erase all health in one frame. Enemies leaving the playfield must be removed and cannot permanently block wave completion. Offscreen bullets and finished particles are removed. Health cannot become negative or exceed its initial maximum.

Use delta time and cap unusually long frame deltas. Resizing preserves playable bounds and sharp graphics without starting duplicate loops. Prevent game keys from scrolling while controlling the game, and clear input after focus loss. No runtime network dependency or missing asset dependency. Keep code readable and avoid unrelated tooling.

## Acceptance criteria and QA mapping
1. AC01 / T001: Local entry point loads without errors; polished ready screen includes controls and a working start button/Enter; gameplay is initially inactive.
2. AC02 / T002,T003,T004,T013: Both movement key sets work; player remains within all bounds; simultaneous movement and held fire work; firing has a fixed cadence; arrows/Space do not scroll during play.
3. AC03 / T005,T010: A player projectile visibly collides with an enemy, resolves once, and changes score only for one destruction; HUD matches state.
4. AC04 / T006: Enemies move and waves complete; wave 2 and later visibly increase at least two documented difficulty parameters; enemy escape does not stall progression.
5. AC05 / T007,T008: A hazard damages player, updates health consistently, supplies visible hit feedback and temporary invulnerability, and clamps health at zero.
6. AC06 / T011,T020: Zero health reaches game over; gameplay stops; final score is accurate; button/Enter restart reset all state. At least three successive restarts keep one simulation/input handling path.
7. AC07 / T012: Blur/hidden document clears input and pauses safely; resume works without a large time jump or stuck key.
8. AC08 / T014: At desktop 1440x900 and compact 800x600 viewports, the playfield, HUD, actions and instructions remain visible and usable; resize keeps player within bounds.
9. AC09 / T016,T017: Browser smoke session runs without runtime errors or missing assets; extended play reaches at least wave 3; projectile/entity cleanup keeps work bounded and play responsive. QA records actual browser/version and evidence.
10. AC10: README provides a reliable local launch procedure and controls; external hosting is unnecessary.
